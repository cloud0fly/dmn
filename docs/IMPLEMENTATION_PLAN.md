# DMN 分阶段实施计划

原则：每个阶段都可以单独验证；不提前加入 Subagent、复杂向量库和多人工作流。

当前进度（2026-10-27）：P0–P4 历史实现与证据保留；本轮完成 P5 本地可靠性管理及技术验收。107 项离线测试、3 项浏览器场景、4 次真实模型恢复演练及三轮各 5 分钟模拟耐久测试通过。旧业务库未迁移，P6–P8 未启动；生产长稳等未验证范围见 [P5 报告](P5_IMPLEMENTATION.md)。

## P0 — 双节点通信最小闭环

**目标**：两个 Provider/Model 路由各自绑定独立 DSH 根会话，交换至少五轮消息。

工作项：

1. 初始化 TypeScript 服务、配置解析器、受控日志和错误类型。
2. 基于 `schemas/message.schema.json` 校验业务消息；Node/Topic 参数严格校验。
3. 应用 `sql/001_init.sql`，实现 `model_nodes`、`topics`、`messages`、`deliveries`、`events` 的存储层。
4. 建立 SDK Runtime Adapter：启动与关闭、固定 `sessionId`、输入提交、事件回执和 Idle 等待。
5. 实现单节点锁与 Wake Scheduler；无用户话题时禁止自动通信。
6. 初期允许结构化输出外发消息，但每次都由服务端校验；后续替换为原生工具。
7. 集成测试：A→B→A 5 轮，不存在 Subagent 调用。

交付物：`runtime-adapter`、`message-bus`、`scheduler`、数据库迁移、端到端测试、示例日志。

## P1 — 私有长期记忆

工作项：

1. 实现所有 Memory API 强制 `ownerNodeId` 过滤。
2. 分离 Identity、Episodic、Semantic、Relationship 记忆。
3. 记忆候选提取 → 去重/冲突检查 → 私有写入。
4. 建立 SQLite FTS5 索引；检索结果限制为 3–8 条，并返回来源与置信度。
5. 验证 A 不能读取 B 的记忆；同一历史可形成不同主观记录。

交付物：`memory-manager`、记忆修订/删除 API、隔离测试、检索评估。

## P2 — 半自主调度与限额

工作项：

1. Topic 状态机：Active/Waiting/Paused/Closed。
2. 每 Topic 与 Node 轮数、时长、Token/费用预算；额度在调度前原子预留或校验。
3. 节点 Sleeping/Queued/Running/Cooling 状态；同节点互斥。
4. 限次重试、退避、死信、消息去重与异常对账。
5. 运行测试：双方反复互问达到限额，自动停止，无自发重启。

交付物：`topic-manager`、`policy-engine`、故障恢复与预算测试。

## P3 — DSH Desktop 入口

工作项：

1. 用 MCP 为 DMN Gateway 暴露启动话题、状态、消息、暂停/恢复、结束等工具。
2. 配置项目级 `.dsh/skills/`，验证官方 Skill Catalog 可以发现并加载。
3. 验证 SDK Profile/模型路由与 Desktop Profile 配置独立，避免会话所有权冲突。
4. 若需要自定义 UI，再评估 Cordis 插件，不在此阶段修改 DSH 核心。

交付物：MCP 服务、Desktop 操作演示、接入文档。

## P3-H1 — 输出协议与诊断补强

2026-10-27 完成：修正完整 JSON/记忆示例及人设中的工具冲突；保持严格解码；增加幂等格式错误审计，以及话题内完成/失败/未知/死信计数；修正真实验收包装器，使已确认完成的非法输出交由 Runner 正确拒绝。无需数据库迁移，不新增模型或自动化权限。

验收：87 项离线测试、三轮独立 P0/P1 与并发实测、P2 两项故障恢复、P3 真模型 MCP 回归通过。完整证据与风险见 [补强报告](OUTPUT_PROTOCOL_HARDENING.md)。

## P4–P8 路线调整（2026-10-27）

状态：P4 本地实现与技术验收完成，待用户体验反馈；P5 本地可靠性管理已验收，P6–P8 尚未启动。P0–P3 的实现与历史验收记录保持不变。

决策：先完成双节点可用产品，再加固运行，之后扩展模型网络、提升记忆质量并形成可部署产品。原 P4 的三节点与跨 Provider 工作移至 P6，生产可靠性移至 P5，遗忘与记忆治理移至 P7；原 UI-M1 纳入新 P4，保留原清单作为详细验收依据。

理由与取舍：继续沿用“先扩第三节点”的方案会同时引入交互、兼容和恢复问题，增加定位成本。新顺序先复用现有双节点后端交付用户闭环，再扩展规模；跨 Provider 的交付因此后移。各阶段依次推进，不并行启动多个里程碑。

| 阶段 | 目标 | 主要交付 |
|---|---|---|
| P4 | 双节点交互产品闭环 | 用户回复契约、双节点界面、话题控制 |
| P5 | 可靠运行与恢复 | 故障恢复、对账管理、备份、运行指标 |
| Desktop-N | DSH Desktop 完整原生插件（P5 修复后、P6 前；N0–N5 已实施） | 官方接口验证、原生面板、服务生命周期、安装及真实验收 |
| P6 | 多节点与跨 Provider | Provider 适配、第三节点、多节点调度 |
| P7 | 长期记忆质量与治理 | 检索评估、冲突审核、遗忘与删除策略 |
| P8 | 部署、权限与发布 | 安装升级、访问控制、恢复及发布验收 |

## P4 — 双节点交互产品闭环

目标：用户能够分别与两个独立节点交流，并准确理解节点间讨论与执行状态。原 UI-M1 合并至本阶段，详细要求见 [独立界面待实施清单](UI_IMPLEMENTATION_CHECKLIST.md)。

按顺序完成三个子阶段：

1. **P4.1 消息契约与持久化**：定义用户→节点、节点→用户、节点→节点三种方向；补齐节点回复用户的受控输出、查询和存储契约。回复关联实际输入、可信节点身份与完成轮次，支持幂等和重连恢复；提供必要迁移及兼容性测试，不以私有 Prompt 或完整 SDK 历史充当回复。
2. **P4.2 执行与状态**：诊断长对话严格 JSON 失败，核对当前 SDK 支持的结构化输出能力；验证云端代理、CA 信任和凭据向 SDK 子进程的传递。明确已接收、排队、运行、已回复、静默、拒绝、失败和未知的语义。保持严格校验，不宽松截取输出或盲重试未知结果。
3. **P4.3 独立界面**：实现双节点身份、真实状态、定向交流记录、节点间消息时间线及预算、截止时间、暂停/恢复/关闭控制。优先采用本地 Web 方案，具体技术选型在实施设计中确认；管理接口须具备本地访问保护，正文按不可信数据渲染。

验收：用户分别向 A、B 发送输入，仅目标节点收到；可见回复绑定正确输入和节点。刷新、重连及重复点击不重复入队或调用模型；页面加载不自动授权讨论。暂停后旧轮次不能越权产生效果，预算及私有记忆隔离保持有效。真实浏览器和真实双节点验收记录逐项标注 PASS / FAIL / NOT_RUN；真实模型回归预先确定轮数、重复次数和预算。

交付物：消息契约、必要迁移、后端与界面、自动化测试、真实验收记录、启动及回滚说明。

不包含：第三节点、跨 Provider、复杂动画、语音及桌面封装。用户输入形成长期记忆的基础来源与权限规则须定义；完整质量治理留至 P7。

## P5 — 可靠运行与恢复

2026-10-27：本地首版实现与技术验收完成。新增维护屏障、成套备份/原位恢复、受控恢复 CLI、指标和消息分页；无 SQL 迁移。24 小时真实长稳、磁盘满/断电及跨平台仍 NOT_RUN，当前结果不代表任意故障自愈。见 [契约](P5_RELIABILITY_CONTRACT.md) 与 [验收报告](P5_IMPLEMENTATION.md)。

目标：先在双节点系统上实现可诊断、可恢复、可维护的运行能力。

工作项：

1. 对进程崩溃、SDK 中断、数据库重开、超时、重复输入、提示注入和遗留锁进行故障注入。
2. 提供未知轮次的证据检查、对账及受控人工处理入口；不自动删除锁或重放缺乏完成证明的执行。
3. 建立数据库与 Runtime Home 配套备份、恢复和版本检查流程，并演练恢复。
4. 增加队列深度、投递延迟、轮次耗时、失败/重试率、Token 与估算费用指标；区分预留额度与实际用量。
5. 完善消息分页、运行数据保留、长时间运行测试和操作手册；记忆删除与传播规则衔接 P7。

验收：故障后已确认数据可恢复，未知结果不会盲重放；操作员能够定位停止原因并受控处理。备份恢复演练和长时间运行测试有明确结果；不宣称任意故障自愈。

交付物：故障矩阵、恢复与对账入口、指标、备份恢复工具及运行手册。

## P6 — 多节点与跨 Provider

2026-10-29：按用户追加授权实施 P6-A，仅双节点共享 DSH 模型目录、Host 生成代理及人工选择；第三节点不在本轮范围。离线、真实 SDK 模拟 Host 与原生选择已通过；真实 DeepSeek Account 完成一轮并投递给 GLM，GLM 返回 `INVALID_REQUEST`，跨 Provider 多轮验收未通过。P6 不标记完成。见 [契约](DSH_SHARED_MODELS_CONTRACT.md) 与 [实现及验收](DSH_SHARED_MODELS_IMPLEMENTATION.md)。

目标：在可靠的双节点基础上扩展为多模型消息网络。

工作项按顺序执行：

1. 定义 Provider 适配契约与能力矩阵，明确结构化输出、完成判定、用量、超时、重试及恢复差异。
2. 接入第二个 Provider，先验证双节点跨 Provider 通信，不降低现有输出和权限校验。
3. 引入第三节点，验证多节点路由、公平调度、并发上限和话题/节点预算。
4. 提供受人工控制的节点配置及参与者选择；凭据通过安全配置提供。

验收：三个节点保留各自固定根 Session 与私有记忆，同节点单写者；跨 Provider 真实讨论达到预设停止条件，异常按各自能力安全处理。节点不能自行邀请成员、扩大权限或增加预算。

交付物：Provider 适配层、第三节点示例、兼容性矩阵、多节点自动化与真实验收报告。

## P7 — 长期记忆质量与治理

目标：在 P1 的隔离与生命周期能力上，提高记忆准确性、检索效用和可管理性。

工作项：

1. 建立中文和技术对话检索评估集，记录召回质量及错误注入情况。
2. 评估记忆内容是否受到来源支持，区分对端观点、主观判断和已验证事实；不把模型置信度当作事实证明。
3. 提供来源追踪、冲突审核、版本修订和错误纠正入口；补齐用户消息作为记忆来源的规则与测试。
4. 制定过期、归档、删除、传播撤回及备份中的保留边界，区分业务记忆与 DSH Session 历史。
5. 仅在检索评估证明需要时引入 Embedding，并保留服务端 owner 过滤和替换能力。

验收：检索质量有可比较的基线和目标，错误记忆可追踪并纠正；删除范围与保留例外明确。跨节点隔离、来源权限及提示注入测试持续通过。

交付物：评估集与报告、记忆管理入口、治理策略及迁移/回归测试。

## P8 — 部署、权限与发布

目标：形成可安装、可升级、可恢复的产品；默认面向单用户本地部署，远程访问作为独立模式设计。

工作项：

1. 提供可重复安装、启动、升级及回滚流程，支持数据和 Runtime 状态的版本兼容检查。
2. 完善配置、凭据管理和安全默认值；不将真实凭据写入仓库、消息或日志。
3. 远程模式单独实现身份认证、授权、来源校验与访问审计，不能直接公开现有受信任本地 MCP 能力。
4. 按实际部署需求评估桌面封装或更深的 Cordis 集成，不预先修改 DSH 核心。
5. 制作发布包、支持矩阵、用户文档和完整端到端发布验收。

验收：新环境按文档完成安装，已有数据安全升级；失败时按演练流程恢复。支持的平台、版本、部署模式和已知限制明确，远程模式单独通过权限验收。

交付物：部署与发布包、权限设计、升级恢复说明、支持矩阵及发布验收报告。

## 后续阶段共同约束

- 保持独立根 Session、同节点单写者、服务端可信身份绑定和私有记忆 owner 过滤；不引入 Subagent。
- Topic Manager 继续强制预算、截止时间和人工停止；前端及模型不得扩大授权。
- 每阶段按契约、必要迁移、实现、自动化测试、真实验收顺序推进；前一阶段验收后再启动下一阶段。
- 真实 API 验收需要可用凭据、通信权限和明确调用预算；缺失时标注阻塞或 NOT_RUN，不编造通过。
- 不把历史验收当作当前版本保证；保留失败证据，区分环境阻塞、实现缺陷和未验证能力。
- 后续接口需求可提前记录，不提前实施其他阶段；日期与工期在各阶段启动时结合范围和验收资源确定。

## 版本关卡

开始 P0 前必须记录：

- `dsh --version` 的实际输出。
- TypeScript SDK 与 DSH Runtime 包的准确版本及其匹配关系。
- SDK Profile 中能够解析的 Provider/Model ID。
- 是否有可用的 `session/resume`，且重启后能够安全恢复固定 ID。
- Skill Provider、Tool Skill、Agent Instructions 插件是否已启用。
